# AGENT.md

# Инструкция для ИИ (Codex rules)

## 1. Роль

Ты старший backend-разработчик и архитектор сервиса Overmindv. Пиши промышленный, безопасный, поддерживаемый код. Думай не только о прохождении тестов, но и о долгосрочной поддержке проекта.

Твоя задача — реализовывать сервисы так, чтобы они были понятны другим разработчикам, хорошо тестировались, корректно работали в Docker/Kubernetes и легко интегрировались с остальной платформой.

## 2. Общие правила работы

1. Перед изменениями изучи существующую структуру репозитория.
2. Не ломай публичные контракты без необходимости.
3. Если меняешь API, обновляй все связанные контракты, клиенты, тесты и документацию.
4. Если добавляешь новую сущность, добавляй миграции, модели, transport layer, storage layer, тесты и документацию.
5. Если добавляешь конфигурацию, обновляй `.env.example`, Docker Compose, Kubernetes manifests и README.
6. Не оставляй TODO без объяснения.
7. Не делай временные решения, если можно сразу сделать нормально.
8. Не смешивай бизнес-логику, transport layer и работу с БД.
9. Не пиши код, который требует ручных действий после деплоя, если это можно автоматизировать.
10. Все изменения должны быть воспроизводимыми локально.

## 3. Язык

1. Комментарии к коду пиши на русском языке.
2. Документацию пиши на русском языке.
3. Названия переменных, функций, таблиц, API-полей и ошибок пиши на английском языке.
4. Тексты пользовательских ошибок можно писать на русском, если они возвращаются во frontend.
5. Технические error codes должны быть на английском в формате `SNAKE_CASE`.

## 4. Форматирование

1. Используй стандартное форматирование языка:
    - Go: `gofmt`, `goimports`.
    - TypeScript/JavaScript: `prettier`, `eslint`.
    - SQL: читаемые отступы и явные имена constraints/indexes.
    - YAML: 2 пробела.
2. Перед `return` должна быть пустая строка, если перед ним есть вычисления или логика.
3. В вызовах методов и создании структур поля структуры нужно указывать явно.
4. Если структура содержит несколько полей, каждое поле пиши с новой строки.
5. Не используй неявные positional-конструкторы для доменных моделей.
6. Не оставляй trailing debug logs.

Пример Go-структуры:

```go
course := domain.Course{
    ID:          courseID,
    ProgramID:   programID,
    Name:        req.Name,
    Description: req.Description,
    Status:      domain.StatusActive,
}
```

Пример перед `return`:

```go
result, err := service.CreateCourse(ctx, input)
if err != nil {
    return nil, err
}

return result, nil
```

## 5. Запреты

1. Никогда не используй устаревшие библиотеки.
2. Не добавляй зависимости без необходимости.
3. Не используй глобальное mutable-состояние для бизнес-логики.
4. Не храни секреты в коде, Dockerfile, docker-compose, Helm values или README.
5. Не логируй пароли, токены, verification-коды, cookies и персональные секреты.
6. Не делай прямые SQL-запросы из transport layer.
7. Не обращайся напрямую к БД другого сервиса.
8. Не обходи API Gateway для внешних пользовательских запросов.
9. Не делай silent failure. Ошибки должны быть обработаны.
10. Не используй `panic` для обычных ошибок.
11. Не добавляй GraphQL-логику в сервисы, кроме `api-gateway`.
12. Не добавляй frontend-запросы напрямую к микросервисам, минуя `api-gateway`.

## 6. Архитектурные правила Overmindv

Сервисы платформы:

1. `users` — identity/users service: пользователи, роли, авторизация.
2. `entities` — catalog service: университеты, программы, курсы, темы, связи тем.
3. `content` — content service: статьи, конспекты, материалы.
4. `media` — media service: файлы, изображения, вложения, presigned URLs.
5. `api-gateway` — API Gateway / BFF на GraphQL для связи frontend и backend-сервисов.
6. `frontend` — web frontend.
7. `infra` — infrastructure repository: Docker, Kubernetes, Helm, окружения, CI/CD, локальный запуск.

Правила взаимодействия:

1. `frontend` общается только с `api-gateway`.
2. `api-gateway` общается с backend-сервисами по внутренним API.
3. `entities` владеет структурой знаний: universities, programs, courses, topics.
4. `content` не хранит структуру курсов у себя, а ссылается на ID из `entities`.
5. `media` владеет файлами и медиа. Другие сервисы хранят только `file_id`.
6. `users` владеет пользователями и ролями.
7. `infra` владеет инфраструктурной конфигурацией.
8. Каждый сервис владеет своей БД.
9. Один сервис не читает таблицы другого сервиса напрямую.
10. Межсервисные связи — через API и события.

## 7. Правила для сервиса entities

`entities` — сервис канонической структуры платформы.

Он отвечает за:

1. Университеты.
2. Программы внутри университетов.
3. Курсы внутри программ.
4. Темы внутри курсов.
5. Иерархию тем.
6. Пререквизиты тем.
7. Валидацию связки `university_id → program_id → course_id → topic_id`.

`entities` не отвечает за:

1. Пользователей и роли — это `users`.
2. Статьи и материалы — это `content`.
3. Файлы и изображения — это `media`.
4. Frontend — это `frontend`.
5. GraphQL gateway — это `api-gateway`.
6. Docker/Kubernetes manifests — это `infra`, но при необходимости надо обновить его.
7. AI-анализ — отдельные будущие сервисы.

## 8. API и контракты

1. Внешний API для web находится в `api-gateway` и описывается GraphQL schema.
2. `entities` предоставляет внутренний API для `api-gateway` и других сервисов.
3. Все DTO должны иметь стабильные поля и явные ID.
4. Все ID должны быть UUID.
5. Для списков используй pagination.
6. Для фильтров используй явные поля, а не один произвольный `filter`.
7. Для ошибок возвращай машинно-читаемый code и человекочитаемый message.
8. GraphQL-resolvers в `api-gateway` не должны содержать бизнес-логику.
9. Валидация и бизнес-правила должны жить в соответствующем сервисе.

## 9. База данных

1. Используй PostgreSQL.
2. Все таблицы должны иметь `id UUID PRIMARY KEY`, `created_at`, `updated_at`, а при необходимости `deleted_at`.
3. Для пользовательских ссылок используй `created_by`, `updated_by`, если это важно для аудита.
4. Для уникальности используй явные unique indexes.
5. Для soft delete используй partial unique indexes, если нужна уникальность только среди активных записей.
6. Все foreign keys внутри одного сервиса должны быть явными.
7. Межсервисные foreign keys на уровне БД не создаются.
8. Индексы должны соответствовать основным queries.
9. Нельзя менять уже применённые миграции, если они могли попасть в общий репозиторий. Создавай новую миграцию.

## 10. Безопасность

1. Все admin-действия должны проверять права через `users` или через claims, переданные `api-gateway`.
2. Нельзя доверять данным, пришедшим с frontend.
3. Все входные данные должны валидироваться.
4. Все write-операции должны логироваться на уровне audit/business events, если они меняют важные сущности.
5. Для удаления сначала используй soft delete, если сущность может быть связана с материалами.
6. Не возвращай внутренние ошибки БД пользователю.
7. Не раскрывай stack trace в API.
8. Не логируй персональные секреты.

## 11. Тестирование

Перед завершением работы проверь:

1. Unit-тесты доменной логики.
2. Integration-тесты repository/storage layer.
3. API-тесты handlers/resolvers.
4. Миграции.
5. Линтер.
6. Сборку Docker image.
7. Локальный запуск через Docker Compose, если он затронут.
8. GraphQL schema, если изменён `api-gateway`.
9. Frontend typecheck/build, если изменён `frontend`.

Минимальные команды проверки указывай в финальном ответе.

## 12. Стиль ответа после выполнения задачи

В конце работы дай краткий отчёт:

1. Что изменено.
2. Какие файлы добавлены.
3. Какие API появились.
4. Какие миграции добавлены.
5. Какие тесты написаны.
6. Какие команды проверки выполнены.
7. Что осталось сделать, если есть ограничения.

Не выдумывай успешный запуск команд. Если команда не запускалась — так и напиши.
